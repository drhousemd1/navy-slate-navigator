# Hosted release preparation

This is an operational sequence, not deployment approval. No hosted target or final app origin has been selected. The working native stack and recovered stack keep their own configuration. Root `config.toml` is an unresolved release template; `project_id = "obedience"` is a local identifier, not a Supabase project ref.

From `app`, `python3 scripts/prepare-release.py --check` verifies the template and merged function fragments. Once the hosted target and final HTTPS origin are approved, supply both explicitly using `--project-ref` and `--site-url`. The helper prints JSON containing the three required environment values, narrow Auth URL settings and named-function command arrays. It does not run commands, read credentials, select a linked project, write files or resolve DNS. Domain syntax validation does not prove domain ownership or target correctness. Run with Python 3.11+; this Mac's Python can also use pip's bundled TOML reader.

Use CLI **2.122.0** for these prepared command arrays. Verify its version before execution. The current public CLI docs also describe v3, whose flags differ. The pinned [deployment command](https://github.com/supabase/cli/blob/v2.122.0/apps/cli/src/commands/functions/deploy/deploy.command.ts) supports named functions, `--project-ref`, `--use-api` and `--workdir`. Do not omit names, add `--prune`, add a blanket JWT override, or substitute unreviewed CLI versions. The actual executor must pass the plan's environment explicitly, reject competing configuration/environment overrides, and recheck the recorded config hash. This helper is not that executor.

Gateway bypass here preserves these inspected application-auth contracts; it is not permission to make service-key operations public. Supabase documents the [two authentication layers](https://supabase.com/docs/guides/functions/auth-headers). The root settings are taken from the reviewed fragments rather than relying on remote defaults. CLI's [pinned deploy implementation](https://github.com/supabase/cli/blob/v2.122.0/apps/cli/src/shared/functions/deploy.ts) skips disabled functions and can leave a partially updated deployment on failure. A successful upload is not coordinated-release acceptance.

## Order for a later authorized release

1. Establish the exact hosted project, operator rights, final app origin and rollback destination. Capture deployed function versions/settings, Auth URL settings, migration history, account gates, notification delivery/schedules and a verified recoverable data/media baseline. Do not infer hosted state from either local stack. Resolve any deployed `create-demo-user` exposure before proceeding; no retirement command is automated here.
2. Establish maintenance/drain for old clients and **old `message-media` workers**, with notification delivery/schedules inactive and original lifecycle/accounting gates preserved. Do not assume deploying a new function terminates requests already executing. The provider's actual worker-drain mechanism remains a hosted verification input. Replace the three named notification tombstones only after target review; read back their versions and verify 410 behavior.
3. Reconcile the hosted migration ledger against current checked-in migrations and the accepted local database. Apply only the reviewed missing forward changes, in order; do not replay historical migrations, reset, or repair history blindly. The coordinated deletion path requires both `20261027140000_account_deletion.sql` and `20261027150000_deletion_media_scan.sql`, plus their earlier identity/accounting/messages prerequisites. Current Encyclopedia, branding, task and Throne clients likewise require their corresponding later migrations. No automatic migration command is included because the hosted ledger has not been inspected.
4. Deploy the helper's **named application functions** together with the matching client release. `message-media` and `account-deletion` must be the current pair: old media workers do not claim upload attempts and cannot coexist with deletion activation. Read back each deployed entrypoint/version and `verify_jwt=false`; stop on partial failure and retain maintenance. Verify the hosted runtime supplies the same project's `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY`. The current handlers deliberately use these legacy built-ins; migrating to new API-key forms is not part of this configuration change. Do not copy local keys or provider secrets.
5. Set only the reviewed Auth Site URL and exact `/auth` and `/reset-password` redirects. The helper's `authUrlSettingsOnly` is a candidate narrow [Auth settings update](https://supabase.com/docs/reference/api/v1-update-auth-service-config), not an instruction to overwrite an uninspected redirect list. Review any old-origin overlap needed during cutover, then read settings back. Do not run broad `config push`: this sparse template does not describe all existing providers, SMTP, hooks, password rules or session settings. Email templates and SMTP remain separately verified inputs; this preparation sends no email.
6. Before opening account gates/cutover, verify the **hosted actual path** with explicitly authorized disposable identities: live user access, unrelated/anonymous denials, media upload/read and survivor bytes, deletion status/resume after Auth removal, editor/branding permission denial and retry behavior. Retain exact IDs for cleanup. Existing API harnesses deliberately pin local ports and must not be repointed at production. Verify final-origin sign-in/confirmation/recovery URLs, service worker and cached-client behavior. The unresolved manual password submission/device checks remain explicit. Original account activation, branding-owner grant and data/media cutover each retain their existing separate gates.

No push secret provisioning, dispatcher deployment, scheduler creation, delivery enablement, original account grant, remote function deletion or hosted mutation occurs in this preparation. If any deployed version/config differs or worker drain cannot be established, stop with the last verified deployment intact rather than enabling partially compatible account deletion.

The frontend is also intentionally bound: `src/integrations/supabase/configuration.ts` permits production only on the existing Lovable hostnames and original project. A new final domain or a different production project requires a separate reviewed frontend binding change and final-origin build verification. This template does not relax that protection or make an arbitrary chosen origin work automatically.

Offline checks: `python3 tests/release-configuration.test.py` and `python3 scripts/prepare-release.py --check`. Root key names and function settings were checked against the official [v2.122.0 configuration schema](https://github.com/supabase/cli/blob/v2.122.0/apps/docs/public/cli/config.schema.json). These checks establish source configuration/guard behavior; they do not prove hosted routing, worker drain, delivery or cutover.
